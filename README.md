# Shop — Laravel وGo

نسخة مشروع تطبيقات الإنترنت للمتطلبين الأول والثاني. تطبيق المتجر مكتوب بـ Laravel 13
وPHP 8.3. يعمل المستودع بـ Go وPostgreSQL، ويتصل به المتجر مباشرة عبر gRPC.

## تشغيل فوري على Windows

شغّل Docker Desktop، وثبّت Python 3.10 أو أحدث وPostman Desktop. افتح
PowerShell داخل المجلد الذي يحتوي `compose.yaml` ثم نفّذ:

```powershell
powershell -ExecutionPolicy Bypass -File .\Start-Shop.ps1
```

ينشئ الأمر ملف `.env` عند غيابه، ويولّد مفاتيح منفصلة، ويستعيد إعدادات
الحاويات الموجودة عند الحاجة، ويبني الصور ويشغّل الخدمات ويتحقق من منفذي
المستودع. أدخل كلمة مرور المسؤول عندما يطلبها. عند وجود قاعدة قديمة استخدم
كلمة المرور التي تعمل في المتصفح؛ تغيير الإعداد لا يغيّر مستخدمًا موجودًا.
لا يحذف الأمر البيانات السابقة.

يفتح المتجر ومجلد `Postman-Ready` الذي يتضمن مجموعتين جاهزتين للاستيراد،
وعقد gRPC وأجسام الرسائل وبيانات حسابَي العرض. هذه الملفات تُولد محليًا
وتحتوي بيانات دخول، لذلك لا تُرسل المجلد الناتج مع حزمة الفريق.

للتشغيل التالي دون إعادة بناء، استخدم `Start-Shop.ps1 -SkipBuild`. ولتوليد
سيناريو جديد على مشروع يعمل استخدم `Prepare-Postman.ps1`. كل تجهيز ينشئ
منتجًا وطلبًا وحسابين مستقلين. لا تستخدم `-SkipBuild` عند تطبيق تحديث الكود.

[دليل المقابلة الكامل](docs/INTERVIEW_GUIDE_AR.md) يشرح REST وgRPC والتزامن
وإيقاف قواعد البيانات وأماكن الكود. نسخة PDF محدثة مرفقة في `docs`.

على Linux/macOS: `python3 tests/shop_demo.py start --no-browser`.

البناء الأول يثبّت امتداد PHP لـ gRPC واعتمادات Composer. يبدأ المتجر بترحيل
جداول قاعدة البيانات وتهيئة حساب المسؤول. افتح واجهة المتجر على
`http://localhost:8080` وصفحة التوثيق على `http://localhost:8080/docs`. أو استورد `http://localhost:8080/openapi/v1.json`
في Postman.

| الخدمة | مسؤوليتها |
|---|---|
| `api` | Laravel. تتلقى طلبات REST على المنفذ المحلي 8080 افتراضيًا. |
| `postgres` | قاعدة المتجر. تحفظ الحسابات والكتالوج والطلبات وسجل الاسترداد. |
| `warehouse` | خدمة Go الحالية. تدير المخزون عبر gRPC. |
| `warehouse-db` | قاعدة PostgreSQL مستقلة للمستودع على شبكة داخلية. |
| `inventory-recovery` | عامل Laravel يعيد محاولة إرجاع الكمية بعد الفشل أو الإلغاء. |

قاعدة المتجر الافتراضية لهذه النسخة هي `shop_laravel`. يبدأ التشغيل ببيانات
مستقلة عن نسخة ASP.NET Core السابقة. ترحيل بيانات متجر سابق يحتاج تحويلًا
مخصصًا. تحفظ الحاويات القاعدتين والصور في volumes منفصلة.

## المتطلب الأول — REST والأمان

يتألف التطبيق من وحدات `Users` و`Products` و`Orders` و`Notifications`.
تسجّل وحدة الإشعارات إشعارًا لصاحب الطلب عند إنشائه وعند تغيير حالته،
وتعرض أحدث إشعاراته عبر `GET /notifications`. تُحدّث الواجهة القائمة تلقائيًا كل 10 ثوانٍ ما دامت الصفحة مفتوحة ونشطة، وتحدّثها فور العودة إلى التبويب. تتعامل وحدة الطلبات معها
عبر واجهتها البرمجية، ويُحفظ الإشعار مع الطلب أو تغيير الحالة في المعاملة نفسها.

| المسار تحت `/api/v1` | الصلاحية |
|---|---|
| `POST /auth/register`، `POST /auth/login` | عام |
| `GET /users/me` | مستخدم مصادق عليه |
| `GET /notifications` | الزبون. تُعرض إشعارات طلباته. |
| `GET /categories`، `GET /products`، `GET /products/{id}` | عام |
| `POST /products` | المسؤول. الطلب multipart ويشمل صورة JPEG أو PNG أو WebP حتى 2 MiB. |
| `POST /products/{id}/stock-additions` | المسؤول. إضافة رصيد بكمية موجبة ومعرّف عملية UUID. |
| `POST /orders` | الزبون. يرسل معرّفات المنتجات والكميات. |
| `GET /orders`، `GET /orders/{id}` | الزبون يرى طلباته. المسؤول يرى جميع الطلبات. |
| `PATCH /orders/{id}/status` | المسؤول. |

تقبل قائمة المنتجات `category` و`page` و`pageSize`. يرسل العميل بعد تسجيل
الدخول ترويسة `Authorization: Bearer <accessToken>`. تُوقّع الرموز بـ HS256
وتتحقق واجهة التطبيق من توقيعها ومصدرها وجمهورها وانتهائها. يقرأ الخادم الدور
من سجل المستخدم ويطبق ملكية الطلب. فتح طلب زبون آخر يعيد `404`، ومحاولة
الزبون تغيير الحالة تعيد `403`. ينتهي JWT بعد 15 دقيقة.

الحد الافتراضي للدخول خمس محاولات في الدقيقة لكل عنوان IP. يُقفل الحساب
خمس دقائق بعد خمس محاولات فاشلة. ترجع الأخطاء بصيغة Problem Details مع
`code` و`traceId` وحقل `userMessage` العربي. توضّح الواجهة أخطاء الحقول بجانبها وتعرض تفاصيل البنود الناقصة ورقم تتبع أخطاء الخادم. يتضمن التطبيق ترويسات الأمان وCORS وتوجيه عدم تخزين
ردود المصادقة.

## المتطلب الثاني — مخزون Go عبر gRPC

يعرض مسار تفاصيل المنتج `availableQuantity` باستخدام `GetStock`. يرسل المتجر
نداء `Reserve` واحدًا لكل سلة. يقفل المستودع صفوف المنتجات بترتيب ثابت داخل
معاملة PostgreSQL. إذا نقصت كمية أي منتج، يعيد المتجر `409` وتبقى السلة
دون حجز. إذا تعطلت الخدمة أو تجاوزت مهلة نداء gRPC البالغة ثانيتين،
يعيد المتجر `503`.

يسجّل المتجر محاولة الحجز قبل النداء. يحفظ الطلب ويحذف سجل المحاولة في
معاملة واحدة بعد موافقة المستودع. عند فشل الحفظ يحاول المتجر `Release`.
تظل المهام غير المكتملة محفوظة ليعيد العامل المحاولة. يعيد المستودع الكمية
مرة واحدة لكل معرّف، حتى عند تكرار النداء. إلغاء طلب في حالة تسمح بالإلغاء
يسجل مهمة إرجاع مع تغيير الحالة في المعاملة نفسها.

### إضافة كمية

بحساب المسؤول، أدخل **الكمية الابتدائية** في نموذج إضافة المنتج، أو افتح
تفاصيل منتج موجود واستخدم **إضافة رصيد**. الصفر في النموذج ينشئ المنتج دون
تزويد. تحفظ واجهة المتجر المنتج أولًا، ثم تطلب إضافة الكمية. إذا انقطع
الاتصال، افتح تفاصيل المنتج في التبويب نفسه واضغط **إعادة محاولة إضافة
الرصيد**. تُعاد المحاولة بمعرّف العملية نفسه.

يتحقق Laravel من دور المسؤول ومن وجود المنتج، ثم يرسل `AddStock` مباشرة
إلى منفذ المستودع الإداري داخل شبكة الحاويات. عقد الإدارة منفصل في
`contracts/inventory/v1/inventory_admin.proto`. يبقى عقد العرض في Postman
`inventory.proto` بالعمليات الثلاث `GetStock` و`Reserve` و`Release`.

يتوفر للمشغّل أيضًا أمر `stock-add` داخل حاوية المستودع. استبدل
`PRODUCT_UUID` بمعرّف المنتج و`OPERATION_UUID` بمعرّف UUID جديد لكل توريد.

```sh
docker compose exec warehouse /usr/local/bin/warehouse stock-add PRODUCT_UUID 10 OPERATION_UUID
```

يزيد الأمر الرصيد بمقدار 10 وحدات. يسجّل Go معرّف العملية ويحدّث الكمية
داخل معاملة PostgreSQL واحدة. تكرار المعرف بالمدخلات نفسها لا يضاعف الكمية،
وتكراره بمنتج أو كمية مختلفة يُرفض. يستخدم الأمر والواجهة منطق الإضافة نفسه.

### إعادة توليد عميل PHP

عقدا المستودع موجودان تحت `contracts/inventory/v1/`. الكود المولّد
مرفق تحت `laravel/generated`. عند تعديل أي عقد، استخدم `protoc` و`grpc_php_plugin`
من جذر المشروع وأعد توليد كود الطرفين.

```sh
protoc -I contracts --php_out=laravel/generated --grpc_out=laravel/generated \
  --plugin=protoc-gen-grpc="$(command -v grpc_php_plugin)" \
  inventory/v1/inventory.proto inventory/v1/inventory_admin.proto
(cd warehouse && buf generate)
```

## اختبار القبول

يمكن للزبون زيادة كمية كل بند في السلة أو إنقاصها، وحذف بند، وإفراغ
السلة قبل الإرسال. يُحجز المخزون عند إنشاء الطلب؛ طلب `Pending` يحتفظ
بكميته قبل موافقة المسؤول، وإلغاء الطلب يعيد الكمية.

### تنافس 20 حسابًا على آخر قطعة

بعد تشغيل Docker، نفّذ من جذر المشروع:

```powershell
py -3 tests/concurrent_checkout.py
```

ينشئ الاختبار منتجًا مستقلًا بقطعة واحدة و20 حساب زبون، ثم يطلق 20 طلب
شراء بإشارة بدء مشتركة. قد يستغرق تجهيز الحسابات عدة دقائق بسبب حد
محاولات الدخول. عند ظهور `429` ينتظر تلقائيًا، ثم يبدأ السباق بعد جاهزية
الحسابات جميعًا. النتيجة المطلوبة طلب واحد `201` و19 طلبًا `409`، والرصيد
صفر، والطلب الفائز بحالة `Pending`. تُحفظ النتيجة تحت
`.demo/race-…/results.json`.

يقرأ السكربت بيانات المسؤول من حاوية التطبيق، أو من متغيري `ADMIN_EMAIL`
و`ADMIN_PASSWORD` إن عُيّنا في الطرفية. لتخصيص عنوان API استخدم
`--base-url http://localhost:8081` مع المنفذ الفعلي. جهّز الاختبار قبل
المقابلة واترك سجل النتيجة مفتوحًا.

### الاختبار الشامل

استخدم قاعدة بيانات تجريبية. الاختبار ينشئ بيانات ويحقن فشلًا مؤقتًا في حفظ
طلب، ويعلّق المستودع لاختبار المهلة، ثم يوقفه ويعيد تشغيله لاختبار الانقطاع. إذا غيّرت بريد المسؤول أو كلمة مروره،
صدّر `ADMIN_EMAIL` و`ADMIN_PASSWORD` في الطرفية التي ستشغّل الاختبار.
صدّر `POSTGRES_DB` و`POSTGRES_USER` أيضًا إذا غيّرت القيم الافتراضية.

```sh
python3 tests/laravel_acceptance.py
```

يغطي الاختبار وصول صاحب الطلب، ورفض طلب الغير وتعديل الحالة، ونجاح طلب
واحد من عشرين على آخر قطعة، وتعافي المخزون بعد فشل الحفظ أو توقف المستودع.
لتجربة قفل الحساب وتحديد معدل الدخول آليًا، اضبط
`LOGIN_RATE_LIMIT_PERMIT_LIMIT=25` في بيئة الاختبار ثم شغّل الاختبار مع
`SHOP_TEST_LOGIN_PROTECTION=1`. استخدم [تعليمات Postman](tests/postman/README.md)
لتجربة مستقلة للواجهات والصلاحيات.

## قبل المقابلة

1. افتح ملفات PDF الثلاثة في `docs/`. ابدأ بدليل «كيفية تشغيل المشروع».
2. ابنِ الصور ثم شغّل Compose بملف `compose.postman.yaml` الإضافي لتجربة gRPC
   من جهازك. ملف Compose الأساسي يبقي المستودع داخل الشبكة.
3. نفّذ `python3 tests/prepare_demo.py` على بيئة العرض المحلية. ينشئ حسابين
   ومنتجًا وطلبًا وإشعارًا، ويولّد بيئة Postman ومجموعتي أجسام gRPC للتدريب والعرض.
   اتبع [دليل Postman من البداية](tests/postman/README.md) لاستيراد سيناريوهات REST الجاهزة.
4. [جهّز طلبات gRPC في Postman](tests/postman/grpc/README.md) قبل المقابلة،
   وشغّل اختبار القبول على بيئة تجريبية. اعرض نتيجة التزامن وتعافي المخزون.
5. وثّق تعاون الفريق في مستودع Git المشترك. يطلب العرض فرعًا رئيسيًا محميًا،
   ومراجعة زميل لكل طلب دمج، وطلب دمج واحدًا على الأقل من كل عضو في كل متطلب.
